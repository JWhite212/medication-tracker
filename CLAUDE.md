## Architecture

Server-first SvelteKit app (Svelte 5 runes). Pages load via `+page.server.ts`, mutations via form actions with `use:enhance`. No client-side data fetching libraries.

- **`src/lib/server/`** — All database queries and server logic. Never imported from client code.
- **`src/lib/server/db/schema.ts`** — Single file for all Drizzle table definitions.
- **`src/lib/server/auth/lucia.ts`** — Lucia v3 session management. Sessions stored in DB, validated in `hooks.server.ts`.
- **`src/routes/(app)/`** — Authenticated route group. Auth guard in `+layout.server.ts` redirects to `/auth/login`.
- **`src/lib/components/`** — Svelte 5 components using `$props()`, `$state()`, `$derived()`, `$effect()` runes. No legacy `export let` syntax.
- **`src/lib/utils/validation.ts`** — All Zod schemas. Every form action validates input through these.

## Key Patterns

- All timestamps stored UTC (`timestamp with tz`), displayed in user's timezone via `Intl.DateTimeFormat`
- **`wallClockToInstant` in `src/lib/utils/time.ts` is the only answer to "what instant does this local wall clock name?"** `parseDateTimeLocal`, `startOfDay`, `endOfDay` and the fixed-time schedule projection are all delegates; there is no second implementation and there must not be. Three used to answer it independently and all three were wrong. Two shared one algorithm — sample the zone's offset at the wall clock _read as if it were UTC_, then subtract it — which takes its sample `|offset|` hours from the answer and so applies the wrong offset whenever a transition falls in that gap (93 wrong conversions over 78,840 wall-clock hours in nine DST zones, always by exactly an hour, and one of the two writes `dose_logs.takenAt`). `startOfDay` was worse and was **not a DST bug**: it anchored on `<dayKey>T12:00:00.000Z`, which at UTC+12 and beyond is already the _next_ civil day, so it returned tomorrow's midnight every day of the year in 18 zones and a New Zealand account's dashboard listed no doses at all. The replacement **proposes a candidate from the offset a day either side and accepts it only if re-reading the offset at that candidate returns the offset used to compute it.** Iteration is not an alternative: inside a spring-forward gap re-sampling oscillates with period 2 forever, so `while (changed)` hangs and a fixed-count loop returns whichever answer the author's pass count straddled. Probe ±24h, never ±1h — Lord Howe shifts 30 minutes and Chatham sits at +12:45. **Both edge policies are chosen, not emergent, and are asserted:** a gap resolves **forward** and never returns null (the callers are the reminder sweep and the dashboard window, where "no answer" is a silently skipped dose), and an overlap takes the **earlier** instant — the old code picked the earlier one in New York and the later one in London, and stability is load-bearing because `buildOverdueDedupeKey` embeds the resolved slot's ISO string, so a wobbling choice re-sends a delivered reminder.
- **A resolved instant does not carry a civil day, and no caller may infer one from it.** Forward resolution can legitimately roll an instant into the next date: America/Godthab springs forward at 23:00 local, so all 60 minutes of that band are missing on 2026-03-28 and a 23:30 dose _necessarily_ becomes the 29th. The guarantee "forward resolution never leaves the requested civil day" is **unsatisfiable**, not merely unmet — an earlier draft asserted it, and it is pinned as a counterexample in `tests/unit/dst-wall-clock.test.ts`. Do not restate it here. The practical consequence: `projectFixedTimes` (`utils/schedule.ts`) and `computeOverdueSlot` take their day-of-week from `dayOfWeekForDayKey(dayKey)` — the requested **key** — never from the instant, or a Saturday-only medication resolves to a Sunday and its slot vanishes from both the dashboard and the sweep.
- **A civil day is 23, 24, 24.5 or 25 hours; `dayStart + 24h` is wrong twice a year in every DST zone.** Use `endOfDay`. On Europe/London 2026-10-25 the fixed offset ended My Day at 23:00 local and dropped every slot in the last hour, the most common bedtime-medication slot there is — and note that fixing `startOfDay` _alone_ would have moved the invisible hour from 00:00–00:59 onto 23:00–23:59 rather than removing it, which is why the resolver and this landed in one commit. The same arithmetic breaks day **walks**: stepping `i * 86_400_000` from a local midnight emitted the transition day twice and never emitted the far end, so the adherence chart and the medications sparkline lost today's bar for a fortnight after each autumn fall-back. Walk `shiftDayKey` instead — pure calendar arithmetic, no instants. `utils/heatmap.ts` is the one exception and is safe for a stated reason: it anchors at **noon UTC** on the target civil date, and UTC has no DST.
- **A `?from=` / `?to=` day param is a civil day in the user's zone, via `parseDayRangeParam`.** `new Date("2026-04-15")` is UTC midnight, which sat beside SQL grouping `AT TIME ZONE` the profile zone: east of UTC the whole `to` day was excluded ("up to 15 April" returned nothing from 15 April) and west of UTC `from` began partway through the previous day. The `end` edge it returns is **exclusive** — the start of the next civil day — so callers compare with `lt`, and the requested day is inside the range whatever its length. It returns `null` rather than an `Invalid Date`, because Drizzle calls `toISOString()` on whatever it is handed and an unguarded param threw a `RangeError` out of a `load`. `analytics/page-data.ts` still keeps its own `dateParamSchema`; folding it in belongs with the analytics-window work, not before it.
- **A rendered date is either a label or a key, and `preferences.dateFormat` applies to labels only.** `formatUserDate` in `src/lib/utils/time.ts` is the single reader of that preference — the counterpart to `formatUserTime`, same contract. Within it, **the preference owns field order and numeric-vs-named month; the call site owns which fields appear** (`weekday`, `year`), so a day heading and a clinician-facing report can differ in content without either one deciding the ordering. The two named-month values map to a **locale**, not to a literal pattern string, and that is what makes them safe to ship: the default `DD/MM/YYYY` → `en-GB` reproduces every previously-hardcoded format byte-for-byte, so an account that never opened Appearance sees no change. **`YYYY-MM-DD` is the exception and must never be handed to a locale** — `en-CA` emits `2026-04-15` on today's ICU, but field order and separator are CLDR data that is allowed to change and did change for `en-CA` in ICU 72, so a conformant implementation may return `15/04/2026`. `isoDayKey` assembles it from `formatToParts` instead, which is specified per-field, and re-pads the widths — `year: "numeric"` renders a pre-1000 year as `999`, not `0999`. This is not paranoia: `formatUserDate` is reached from `.svelte` components, so it runs against the **viewer's browser** ICU, and a test that only observes output on the server runtime cannot catch the divergence — assert the shape, and pin a year below 1000, which is the one input where locale delegation visibly differs. Keys are the other half, and the same rule binds them: anything compared, grouped or round-tripped goes through `isoDayKey` too — the day keys in `analytics.ts`, `schedule.ts`, `log/+page.svelte`, `medications/+page.server.ts` and `utils/heatmap.ts`, and above all the CSV date cell, which `import/csv.ts` re-reads as strict `YYYY-MM-DD`. Two distinct ways to break that cell: routing it through the preference (a user on `MM/DD/YYYY` exports a file their own account refuses to import), or leaving it to a locale (the year loses its padding, and a CLDR change reorders the column outright). A key is only ever exempt from the _preference_, never from being built rather than borrowed.
- Live "time since" counters: client-side `$effect` + `setInterval(60s)` + `visibilitychange` recalc. No WebSocket.
- **Dashboard time is server-relative, and `createDashboardClock` (`components/dashboard/dashboard-clock.ts`) owns it.** `(app)/dashboard/+page.svelte` creates one clock **seeded from the page payload** — `createDashboardClock(invalidateAll, { now: data.now, nextRefreshAt: data.nextRefreshAt })`, the first payload only — puts it in context with `setDashboardClock`, and calls `clock.sync({ now, nextRefreshAt })` once per payload. The seed sets the skew and the refresh instant **without arming the timer**: unseeded, the clock read `NaN` until the first `sync`, and arming at construction would leak a `setTimeout` out of SSR. `sync` re-measures `skewMs = Date.parse(data.now) − Date.now()` (`skewFrom`) and arms the ONE refresh timer for `data.nextRefreshAt` (computed by `composeDashboardPageData`, clamped to at least `now + 5s`). `onVisible()` re-checks on `visibilitychange`, and the page re-renders durations from a 60s `clock.serverNow()` tick. Every payload instant is compared with `serverNow() = Date.now() + skewMs`, never raw `Date.now()`: a device clock minutes fast would otherwise reload the page in a loop, and the stale guard would refuse every tap near a boundary. **The stale guard is `clock.isExpired()`** (`serverNow() >= nextRefreshAt`, false while the refresh instant is `NaN`), and only dashboard controls hand the clock to `createDoseWrite` as `staleGuard`, so /log and /medications have no guard by construction rather than by a check that could be wrong. Status, rows and buttons change only through the load; the client never re-derives them, and nothing else arms a refresh timer.
- All DB queries scoped by `user_id` — never trust client-provided user context
- Audit log (`src/lib/server/audit.ts`) records all create/update/delete with JSONB diffs
- `updatePreferences` in `src/lib/server/preferences.ts` is the **only** audited write path for user preferences — it reads the before-image, writes, and logs the diff itself. Callers (the six appearance field actions, the notifications and data form actions, and the `/api/v1` `update_preferences` command) just call it; never re-hand-roll a `computeChanges` subset at a door, and never write `user_preferences` directly. The diff is scoped to `Object.keys(updates)` because `updatedAt` is rewritten on every save and a whole-row diff would log a change on a no-op. **The before-image comes from a locking CTE inside the write** (`WITH previous AS (SELECT … FOR UPDATE)`), not a prior `SELECT`: instant save means two requests for the same field overlap, and a separate read let both diff against the same row so the second change was never audited. Because the correctness is decided by the database, that test lives on PGlite (`tests/unit/pg/preferences-audit.test.ts`) and the whole `preferences` suite moved with it — `fake-db` has no `$with`, no update `.from()` and no select `.for()`, and per the test-seam rule it must not grow them.
- **`src/lib/appearance/` is two modules on purpose.** `registry.ts` is metadata — key, group, label, control kind, DOM binding — with **no zod** and only `import type` from `$lib/types` (itself a type-only import of the drizzle schema), because the appearance page imports it and nothing client-side reaches zod today (`tests/unit/appearance-bundle-boundary.test.ts` holds that line, erasing type-only edges because six `.svelte` files reach zod through them). `schema.ts` imports the registry plus zod and is imported only from server files. **The bound belongs to the arity, not the option:** the form door is a `strictObject` with one required key per action, the `/api/v1` door is all-optional and JSON-native, and the import door is all-optional and bounded. Collapsing them changes behaviour at whichever door loses — `heatmapPeriod` was the proof, and an all-optional form door is worse than a no-op, because the checkbox transform fires on an empty parse and writes `false` over the user's setting.
- **`src/lib/preferences/schema.ts` owns the value domain of the seven preferences the appearance registry does not — and owns it as data, not as a `satisfies` clause.** Its key set is `Exclude<PreferenceKey, AppearanceKey>`, derived by subtraction, so a new `user_preferences` column is a compile error until some door claims it. The domains themselves (`DOSE_LOG_PAGE_SIZE_BOUNDS`, `HEATMAP_PERIOD_BOUNDS`, `EXPORT_FORMATS`) are written once and both API arities are `optionalise()` of the same object, because **a `satisfies` clause pins the key set and the output type but never a bound** — `z.number().int()` and `z.number().int().min(1).max(3650)` both satisfy `z.ZodType<number | undefined>`, which is exactly how `heatmapPeriod` shipped unbounded at `/api/v1` and bounded on import. The appearance six escaped that only because none of them carries a numeric bound. Divergence is still permitted (the bound belongs to the arity), it just costs a visible override line plus a named entry in `INTENTIONAL_DIVERGENCES`; what it can no longer be is accidental. `analytics/page-data.ts` imports `HEATMAP_PERIOD_BOUNDS` for its read-side clamp rather than restating it — the narrow exception to the `MAX_INTERVAL_HOURS` "door policy, not read policy" rule, because a stale value here costs only a shorter heatmap, not a medication dropped from forecasting.
- `tests/unit/preference-door-conformance.test.ts` is the backstop, and its probe values are derived from **each door's own schema** (`instanceof z.ZodNumber` plus `.minValue` / `.maxValue`, `.options` on an enum — all public in zod 4.3.6), then unioned across both doors. That union is the trick: when one door is bounded and the other is not, the bounded side contributes `max + 1` and the unbounded side is the one that accepts it, so drift is caught whichever door is narrower. Hand-writing those probes would make the test a fourth restatement of the domains it checks. The separate hardcoded cases (`heatmapPeriod` 1–3650, `doseLogPageSize` 5–100, `exportFormat`) are the other half and are not redundant: derived probes move with the schema, so only a pinned literal notices both doors widening together.
- Inventory auto-decrements on dose log, auto-restores on delete
- Refill forecasting lives in `src/lib/server/inventory.ts` — single source of truth for daily-rate selection (schedules first, legacy columns next, 30-day history for PRN). Both `dashboard/+page.server.ts` and `medications/+page.server.ts` consume it. The same module owns severity classification (`critical ≤3d`, `warning ≤7d`, `watch ≤14d`).
- Analytics insights are deterministic — `buildInsights` in `src/lib/server/analytics.ts` is a pure function over already-computed stats. Add new rules by writing a small predicate that returns `Insight | null`; never inject prescriptive medical wording.
- **The expected-doses denominator has exactly one owner, split across two functions.** `expectedPerDayFor` in `analytics.ts` owns the rate (schedule rows first; the deprecated legacy column only for `scheduleType === "scheduled"`, or a PRN med gets a fabricated denominator), and `lifecycleEnd` in `analytics/lifecycle.ts` owns where the window closes. `getPerMedicationStats` and `getDailyAdherenceSeries` both consume them — they used to spell this quantity out independently and disagreed four ways, so the same page showed a falling adherence chart beside a healthy headline stat. Never re-derive either at a call site.
- **`getDoseStatusBreakdown` aggregates PER MEDICATION; pooling first is a different and wrong quantity.** `expectedTotal` deliberately excludes a PRN medication and `takenEvents` deliberately includes it, so a pooled numerator and a pooled denominator range over **different medication sets** and subtracting one from the other is meaningless. Shipped for months: 20 of 30 scheduled doses taken plus 15 PRN doses printed "Missed 0, Adherence 100%, Overuse 16.7%" on the clinician PDF beside the analytics page's own 67% for the same window. It is **not a PRN bug** — two ordinary scheduled medications reach it, one's surplus settling the other's debt (30 expected/5 taken beside 10 expected/35 taken reported 0 missed), which is why the clamp moves inside the sum and the fix is keyed on `m.expectedTotal` rather than on `scheduleKind`: a schedule-kind-keyed fix passes every PRN fixture and fails that one. `includeAsNeeded: true` therefore **stays** — a medication expecting nothing now contributes 0 to every term by construction, whereas flipping the flag would "fix" the ratios by deleting real doses from the PDF's "Taken events" line. Three fields are per-medication sums (`missedEvents`, and the numerators behind `adherencePercent`/`overusePercent`); `takenEvents`/`takenQuantity`/`skippedEvents` stay unclamped factual counts over every medication, and the bar's segments consequently do not sum to `expectedTotal`. **Adherence takes a numerator capped per medication and overuse an uncapped surplus, and they must never share one:** a capped numerator satisfies `taken <= expected` unconditionally, so `calculateOveruse` returns 0 forever and `export-pdf.ts`'s `> 0` gate deletes the line — 45 doses against 30 expected reporting nothing. Symmetrically, dropping the `expectedTotal > 0` guard on the surplus readmits every as-needed dose as overuse, which is worse than the pooled figure it replaced.
- **`clampEffectiveDays` charges whole days only, and its range is closed at `rangeTo`.** It used to `Math.round` a millisecond duration, so the extra expected dose arrived at **local noon** — twelve hours into the partial day, with no user action — and rendered as a red Missed segment, a clinician-facing missed count and a "Lowest adherence" insight. Rounding up is the costlier error here, so a partial day is not charged; `Math.ceil` is the same mistake made sooner (a medication added six hours ago acquiring a full day of expectation). **Every pre-existing fixture sat on a whole number of days, which is why 1825 green tests said nothing about the rounding mode** — the probes either side of the boundary in `tests/unit/analytics-lifecycle.test.ts` are what pin it, and two are needed on the round side because one at the 0.5 tie leaves `Math.round` alive for 15.75. **The tolerance is `RANGE_SHORTFALL_TOLERANCE_MS` — two hours and one millisecond, and every part of that is load-bearing.** The millisecond is `lastIncludedInstant`'s: `export-pdf.ts` hands the breakdown `to - 1ms` so its summary counts exactly the rows the dose table beneath it lists, and a plain truncation scores that 30-day report as 29. The two hours are because **the PDF's bounds are LOCAL midnights** (`api/export/+server.ts` builds them with `parseDayRangeParam(..., tz, ...)`), so a civil range containing a spring-forward is one transition short of `days * 24h` — a millisecond of slack alone printed "Expected events: 30" over 31 days of London doses and added an "Overuse: 3.3%" line to a patient with perfect adherence, and a single-day report on the transition day read "Adherence: 0%". Two hours because that is the **widest transition in the IANA database** (Antarctica/Troll, UTC+0→UTC+2; Chatham's +12:45 is an offset, not a transition size), and a range can never be short by more than one transition since any further spring-forward is preceded by a cancelling fall-back. A test scans every zone the runtime knows and fails if tzdata ever widens that bound. **The cost is stated rather than hidden:** a partial overlap of 22h or more is charged a whole day — a re-widening of the same defect, but to 22h from `Math.round`'s 12h, and only at a lifecycle edge rather than on every window every day. It still measures 24-hour days in UTC milliseconds and only _tolerates_ civil ones, while `getDailyAdherenceSeries` genuinely counts day keys via `isActiveOn`, so **the two denominators still part company on a lifecycle edge falling mid-day**. Converging them needs a civil-day counter and a timezone here, and first needs the two doors to agree whether `rangeTo` is inclusive (the PDF's last included instant) or exclusive (the analytics page's UTC midnight) — a distinction that vanishes in day-key space. Deliberately not done here.
- **Archiving: `archivedAt` for questions about the past, `isArchived` for questions about the present.** No UI writes `endedAt` — it arrives only via import or `/api/v1` — so archiving is the only "I stopped taking this" event a web user produces, and it sets `archivedAt` alongside the flag. Anything measuring a _window_ (the expected-doses denominator, adherence, missed counts) goes through `lifecycleEnd`, never either column alone: filtering on the dateless `isArchived` erased what had been expected on every _past_ day too, so archiving retroactively improved your history. Anything describing _current state_ (the heatmap's scheduled-hour highlight — "what does my schedule look like") reads `isArchived`, because there is no window to clamp against. Both live in `analytics/page-data.ts`; they are not interchangeable.
- **`src/lib/utils/schedule.ts` is the single owner of the dashboard's answer to "has this slot been handled?" — the window, both clips and passes 0–2 — and nothing on the dashboard re-derives any part of it.** The reminder sweep answers the same question independently: `computeOverdueSlot` (`reminders/domain.ts`) walks its own look-back rather than calling into this module, and the two share only `CARRY_OVER_MS` and the `getLocalDateString` day-key helper. Converging them is due-ness unification work, not assumed here. `dashboardWindow` owns every bound. Projection runs from yesterday's local midnight (a day-key walk, never `todayStart − 24h`) to one `MATCH_TOLERANCE_MS` past `end`. `visibleStart` is the first millisecond under `CARRY_OVER_MS` old. **Tomorrow's first hour is matched but never returned**: without it, pass 1 at tomorrow's view takes a late-evening dose that pass 2 gave one of today's slots at today's view, and that row reappears as overdue at midnight. `projectMedicationSlots` owns both clips. The lifecycle clip drops everything outside `startedAt`/`endedAt`, so a medication added at 14:00 has no 08:00 slot. The schedule-edit clip drops any slot before `todayStart` that is older than the medication's earliest `effectiveFrom`: every save rewrites the rows with `effectiveFrom = now`, so the current rows say nothing about yesterday. `matchMedicationSlots` runs the passes over one medication, sharing **one** capacity map (`max(1, quantity)` for taken, 1 for a skip or missed row):
  - **Pass 0**: a taken dose at exactly a slot's instant claims it, with the smaller id winning a tie. So "Took it at 09:00" next to an open 08:55 resolves 09:00.
  - **Reserved skip**: a skip on one of the medication's slot instants is a pass-1 candidate for that slot only and never enters pass 2. So a real taken dose within the hour still beats it.
  - **Pass 1**: the shipped ±1h rule (taken over skipped/missed, then distance, then id) over what pass 0 left, with the **segment limit**. A dose must be taken before its slot's segment ends (`todayStart` for yesterday's slots, `end` for today's, no limit for tomorrow's first hour). So a 00:10 dose goes to today's 00:13, not yesterday's open 23:30.
  - **Pass 2**: leftover taken/skipped capacity with `takenAt ≤ now`, replayed in `(takenAt, id)` order. Each dose walks backwards from the last slot strictly before it, skipping resolved slots, and stops below `pass2Bound` (`visibleStart` with a window, `dayStart` without). A dose never resolves a slot after it.

  An unresolved slot is overdue or upcoming by time alone, even if it holds a missed row. Two proofs live in `tests/unit/schedule-matching-properties.test.ts`. One is a seeded differential against `tests/unit/helpers/legacy-slot-matcher.ts`, a **verbatim** copy of the pre-change matcher: never "fix" it, because a corrected oracle compares against nothing. The other is a seeded midnight/noon stability check. Anything that needs to know what a write would do must re-run these functions, never approximate them.

- **The dashboard and Analytics disagree about late and multi-unit doses, deliberately.** The dashboard answers "has this slot been handled?", with capacity and late resolution. Analytics counts dose events per civil day of `takenAt` (`analytics.ts`, under the denominator rules above). They already differed inside ±1h: one ×3 dose fills three slots on the dashboard and counts once in Analytics. Pass 2 extends that to late doses. A dose logged today can resolve yesterday's Earlier slot on the dashboard while Analytics files it under today. Converging the two would reverse a product decision either way: a late dose resolves the slot it was for, and logging now records the current time. So do not bend one surface to match the other; convergence belongs with the analytics-window (W1) or due-ness work. The "pinned divergence" test in `tests/unit/schedule.test.ts` holds this: fixed 08:00/14:00/20:00 and one ×3 dose at 20:30 give all three slots taken.
- **`src/lib/server/analytics/page-data.ts` owns the analytics page's composition.** `resolveAnalyticsQuery` turns the query string into the current and previous windows; `composeAnalyticsPageData` builds the payload from already-fetched results. `analytics/+page.server.ts` is I/O only — resolve, fetch, compose — so new derived values belong in the module, not back in the `load`. It sits beside `analytics/lifecycle.ts` rather than in `analytics.ts`, which is already 720 lines of queries plus pure helpers.
- **`src/lib/server/dashboard/page-data.ts` owns the dashboard's composition, and no matching rule.** `composeDashboardPageData` sorts what `utils/schedule.ts` decides (window, projection, passes 0–2, `slotActions`) into Earlier/Today cards, Done, Later, the header status and `nextRefreshAt`; `dashboard/load.ts` is I/O only — four queries, then compose. It adds exactly one rule, a presentational one: a due-now row that shows Log now does not also show Took it at. `projectFixedTimes` is called once per medication here and handed to `slotActions`, because it is the only projection step that touches `Intl`. If a count on the page disagrees with a slot's status, the bug is in this module, not the matcher.
- **Log now, Took it at and Skip re-derive `slotActions` under the medication lock, through `recomputeSlotActions` in `doses.ts`**, which runs the same `projectFixedTimes` / `slotActions` the page load ran. A button is a claim about the page the user was looking at, and a second device makes it false: phone A's Log now at 08:40 resolves the 08:00 slot, and laptop B's stale "Took it at 08:00" used to insert a second taken dose and take stock again, because the only check was a row at the exact posted instant. `logDoseAtSlot` keeps that exact-instant check first, so a double tap still gets its specific message, then throws `SlotTargetChangedError` unless `rows.get(slot)?.tookItAt === slot`. That also refuses Took it at on a slot a skip has already resolved: remove the skip first. **Took it at and Log now are always ×1**, whatever quantity is posted: the simulation proves a probe of quantity 1, and a larger dose could resolve rows it never checked. Skip posts `forSlot`, and `skipDoseForSlot` writes at the server's `rows.get(forSlot).skipAt` — `min(slot, now)`, the instant the simulation proved — so no client clock picks it. A page loaded before this shipped posts `takenAt` only; for one release that goes through `skipDoseForSlot` too, which accepts it exactly when it names a past slot and otherwise answers 409. A tab loaded before this release runs the old client, which neither polls for a new version nor checks `updated.current`, so it keeps getting that 409 for a Skip on a slot still ahead until it is reloaded by hand. From this release on, `kit.version.pollInterval` and `reloadDocumentIfUpdated()` make a 409 reload a stale tab onto the new code. Delete the `takenAt` legacy path one release after it ships.

## Reusable Components

- **`Sparkline.svelte`** — inline-SVG line trend, no chart library. Pure path generation lives in `src/lib/utils/sparkline.ts:buildSparklineShape` so it's unit-testable. Used on Analytics stat cards (adherence + dose volume) and per-medication on the Medications list.
- **`EmptyState.svelte`** — standardised empty-state card. Props: `illustration`, `illustrationAlt`, `title`, `body`, `action` (`{ href?, label, onclick? }`). Used on Log and Medications; hold the line on consistency when wiring it into more pages.
- **`InsightsCard.svelte`** / **`StatusBreakdownBar.svelte`** / **`RefillsCard.svelte`** — analytics + dashboard surfaces; render nothing when their dataset is empty (don't wrap them in `{#if}` at the call site).
- **The landing-page walkthrough (`src/lib/components/walkthrough/`) draws the dashboard; it never mounts it.** Its stage parts (`parts/dashboard/Stage*.svelte`) copy the real components' layout classes and reuse only their pure leaves — `MedicationGlyph`, `StatusMarker`, the copy helpers in `utils/dashboard-copy.ts` and `utils/time.ts`, and the rules `RefillsCard` and `StatusBreakdownBar` export from `<script module>`. The real `DueCard`, `DoseActionForm` and `QuickLogBar` are focusable and need the write lock, the dashboard clock, `use:enhance` and `$app/state`, and `DashboardHeader`, `DoneList` and `LaterList` render headings, landmarks, fixed ids and `tabindex="-1"` targets that would be duplicated across the desktop and the phone. The stage is `aria-hidden` and holds nothing focusable, and its motion comes only from `Frame` values, which are pure functions of T: no part carries an `animate-*` or `transition-*` class. **Five test files keep it honest, because a stale or broken scene fails silently.** `tests/unit/walkthrough-demo-facts.test.ts` holds History's unfiltered list and the Medications "Last taken" timers to the one dose list, `DEMO_DOSES`. It holds the Security expiries to `formatUserDate`, and `STAGE_REFILLS` and the demo's `refillWatch` flags to `classifyRefillSeverity`. It holds the Analytics bar to the real `foldDoseStatusBreakdown` over the seeded `HISTORY`, which differs from `DEMO_DOSES` on 23 Sep on purpose. `tests/unit/walkthrough-dashboard-fidelity.test.ts` runs the real `composeDashboardPageData` at each story moment in `demo-dashboard.ts` (desktop and phone, before and after the log). It asserts that the scenes' data equals the composer's output and that their rendered text equals the copy helpers'. So a change to the composer's rules or a copy helper's wording fails there, instead of leaving the landing page advertising the old app — which is what happened when #170 rebuilt the dashboard and the walkthrough kept drawing the deleted one. Section titles and button labels are restated by hand in the Stage parts and the oracle, so renaming one in `DueCard`/`DoneList`/`LaterList`/`dashboard/+page.svelte` means renaming it in the stage too. Every key `computeFrame` reads must be listed in `REQUIRED_MARKS` (`timeline.ts`) and registered from mount, at every T, on exactly one element under its own root. `walkthrough-timeline.test.ts` records the reads through a `Proxy`, and `tests/unit/walkthrough-stage.svelte.test.ts` mounts the stage, checks the registry at seven moments from the title card through the phone beat and fails on any focusable element, and `tests/unit/walkthrough-video.svelte.test.ts` asserts the `aria-hidden` wrapper that covers the whole stage, but not the caption or the pause button. A missing mark throws nothing: the camera falls back to the wide shot and the cursor to the window centre. Marks are also measured only while the stage mounts, with T still on the title card, so an element drawn later is never measured. That is why a collapse or a new row is drawn with height, opacity or transform, never with an `{#if}` whose condition changes with T around a marked element; a payload-fixed condition such as `StageDueCard`'s `{#if row.logNow}` cannot change the registered set and is allowed.

- **`src/hooks.server.ts`'s `handleError` is the only observer of an unexpected server failure, and `src/lib/server/log.ts` is the only writer of a server log line.** SvelteKit calls `handleError` for errors nobody threw on purpose — an `error(400, …)` from an action or a load bypasses it — so everything reaching it is a genuine crash. It mints a short random correlation id, writes ONE structured JSON line, and returns `{ message, errorId }`. **That return value is serialised into the page, so it must carry nothing from the exception**: the message is a fixed string, the id is random, and the query string is deliberately not logged because `?q=` on the dose log is user text. Both `+error.svelte` boundaries render the id as selectable `<code>`, and only when there is one. What must never enter a log line: request bodies, cookies, headers, email addresses, medication names, dose notes — `userId` is the only identifier worth carrying. Three `console.warn` calls remain on purpose, in `utils/contrast.ts` and `routes/+layout.ts`, because both are **client-reachable** and cannot import `$lib/server/*`; `tests/unit/server-log.test.ts` scans `src/` and asserts that exemption list is exactly right **in both directions**, so a stale exemption fails as loudly as a new offender.
- **`actionErrorMessage` in `src/lib/utils/form-errors.ts` is the single reader of a failed form action.** The `(app)` actions return four different failure shapes — `{ errors: { field: [...] } }`, `{ errors: { form: [...] } }`, `{ error: "string" }`, and a bare `fail(400)` — plus `result.type === "error"`, which carries `App.Error`. Every call site that wanted to show a failure had to know all five, and three of them knew none and showed nothing at all. Never re-read `result.data` at a call site. **A `use:enhance` callback that handles only `result.type === "success"` is a silent failure**, not a shorter one: `logDose` returns `fail(404)` for a medication deleted in another tab, so the button spins and the user believes the dose was recorded.
- **`src/lib/components/dose-writes/` is the single client path for every dose write, on every page.** `createDoseWrite` (`dose-write.svelte.ts`) is the only `SubmitFunction` for a log, a skip or a delete: the dashboard's `DoseActionForm` (Due cards, chips, the 1–9 shortcuts, Done's _Remove skip_ and _Remove_, the edit dialog's _Remove this dose_), the /log × in `TimelineEntry` and the /medications card's Log all sit on it. Neither kind of Undo is a form: a create's Undo (`/dashboard?/deleteDose` with `forUndo=1`) and a delete's restore (`/dashboard?/restoreDose`) are both posted by the Undo registry's `runUndo`, below. It reads its options at submit time and runs, in this order: `beginDoseWrite`, the stale guard (dashboard only), withdrawal of any Undo offer naming this dose (only now, when the write is certain to be sent, so a refused tap never costs the user their Undo), then the POST. **`beginDoseWrite(cancel, lock)` (`begin-dose-write.ts`) is the one owner of "may this write start?"**: the offline check first (`navigator.onLine === false` sends nothing and takes no lock, so an offline tap does not lock every control for the cooldown), then `acquire()` on the one write lock. A refusal has already called `cancel()` and, unless only the cooldown refused it, told the user, and holds nothing; `true` means the caller holds the lock and releases it in a `finally`. Its callers are exactly `createDoseWrite`, `DoseEditForm`'s Save and the medications ↑/↓ reorder, and `tests/unit/begin-dose-write.test.ts` pins that list and scans `src/` for any other `lock.acquire(` or `OFFLINE_WRITE_TOAST`, so a gate written out a second time fails the suite. `createDoseWrite` handles every result itself — the toast or the Undo offer, focus, and every failure through `actionErrorMessage` — because nothing calls `update()` (next bullet). A success reads `respondedAt = Date.now()` before anything else, because the reload after it can wait out a navigation or an outage: `buildToast(doseId, respondedAt)` receives it, so a toast that names a time (the medications card's "logged at") names the response's arrival, and the Undo offer's deadline counts from it. **The lock belongs to the `(app)` layout**: `+layout.svelte` calls `setDoseWriteLock(createDoseWriteLock())` once per layout instance, never as module state, which is per-process during SSR. Toast and every page's dose controls read that same lock, so an Undo pressed after navigating holds the lock the new page reads. Controls signal it with `aria-disabled`, never `disabled`, which drops focus to `<body>`. The medications ↑/↓ reorder takes the lock through `beginDoseWrite` too, because it moves the keyed cards and a Log tap could otherwise land on a different card; it is not a dose write, so it keeps `update()`. A tap refused while a write is `active` (a holder exists; `busy` also covers the 700ms cooldown) toasts "Still saving your last change…" — a reorder refused mid-write says it too, and an offline one shows the offline toast — and the "Still saving…" toast is never stacked: a refused tap restarts its timer instead. That is `showToast(…, { coalesce: true })`, which only `beginDoseWrite` and Toast's refusal of an Undo pressed mid-write pass; every other identical toast stacks, because a second "Undone" or "Dose not found" is news and a polite live region never announces a restarted timer. No toast's timer starts while the pointer or focus holds the stack (WCAG 2.2.1). A tap refused by the cooldown alone says nothing. **Edit Save is the one exception**: `DoseEditForm` keeps its own enhance because its field errors render inline, but its submit starts through `beginDoseWrite`, so Save and Remove exclude each other; it withdraws the Undo offer for the dose being saved, clears any offer once the Save lands, and reloads through `reloadAfterWrite`. A second hand-rolled enhance anywhere reopens the double-tap double-dose the lock exists to close. The /log × and the medications card's Log render `type="button"` until mounted, so a tap before hydration does nothing rather than posting natively with no Undo. The 1–9 shortcuts `requestSubmit()` the chip form `findQuickLogForm` returns, which matches `form[data-quick-log]` only because a Due card's _Took it at_ is also a `?/logDose` form and records a past instant; `KeyboardShortcuts` ignores `e.repeat` and does nothing while any `[aria-modal="true"]` is open, except `?` closing its own help overlay. A write button swallows a repeated Enter keydown, because Enter activates on keydown and repeats. Dose controls take their size from fixed height classes of at least 44px (`h-11`, `min-h-11`, `size-11`), never from padding (the /log row's ✎ and × are the one exception, per spec Section 3: `size-8 pointer-coarse:size-11`, 32px for a mouse and 44px on a coarse pointer), and the Quick Log `li` is `box-content` so its 1px border does not clip each chip segment to 42px.
- **No dose write calls enhance's `update()`; reloads go through `reloadAfterWrite()` (`dose-writes/reload-after-write.ts`).** `update()` applies a result only while the action's path matches the page the user is on when the result arrives, so once dose writes post across routes — the medications card's `/dashboard?/logDose`, an Undo pressed from any page — it dropped their failures silently, and it runs `reset_focus` on whichever page matches, which sent focus to `<body>` after the edit Modal had returned it. **`Modal` returns focus to the control that opened it only while that control is still connected**; a write refused because another device had already removed the dose leaves the dialog open while its reload drops the row the Edit or ✎ sat in, so on close it falls back, only if focus is lost, to the caller's `returnFocus`, else `pageHeading` without scrolling. The dashboard's edit dialog passes its Done heading, the same target its Remove passes as `focusAfter`, and must: closing the dialog in `onSuccess` runs Modal's fallback in the tick before the write judges focus, so a dialog hosting a dose write whose `returnFocus` differed from that write's `focusAfter` would win. `reloadAfterWrite` does three things in order. It waits out a navigation in flight (`navigating.to !== null && !navigating.willUnload`, then `await navigating.complete`, whose rejection on an aborted navigation is swallowed), because an `invalidateAll()` issued mid-navigation aborts that navigation. After a write whose outcome is unknown — a network error, with no status — it waits for the server: for the `online` event while offline, and otherwise by probing `fetch("/api/health", { cache: "no-store" })` with 2/4/8/16s backoff and then every 30s (`HEALTH_PROBE_BACKOFF_MS`), re-probing early on `online` and on `visibilitychange` → visible, and counting anything but `res.ok` as unreachable, because the service worker answers a failed GET with a synthetic 503. `online` alone is not enough: after a reset connection, or a PWA backgrounded mid-request, it may never fire. Then it runs `invalidateAll()`. **The lock stays held until that reload lands**: a retry against data nobody has checked is how a duplicate dose happens. Navigation still works meanwhile. `createDoseWrite` reloads after every result, every failure included: a 404 means the page shows a dose another tab removed, and left on screen it gets the same 404 on the next tap (`DoseEditForm` reloads after a refusal for the same reason). Only a 409 reloads the whole document instead, when `updated.current` is true (`kit.version.pollInterval` is 300s), because `invalidateAll` refreshes data, not JavaScript, and an installed PWA can stay open for days running code that posts an old shape. `applyAction` runs only for a `redirect`. Focus belongs to the primitive alone: on success and on failure it moves only if it was lost (`isFocusLost`: `<body>`, a disconnected node, or inside `[data-toast-stack]`), to the caller's `focusAfter`, else back to the control tapped, else — when the reload removed that control, as a 404 for a medication deleted elsewhere does to the /medications card and a Quick Log chip — the page's h1, focused without scrolling, and never onto a different dose's write button; success judges this after `onSuccess` and a tick, so a dialog that `onSuccess` closes over the focused button counts as lost. The h1 is gated on there having BEEN a control: with nothing focused at the tap (Safari focuses no button it taps, so on an iPhone that is every tap) the write took nothing away, and parking focus on the heading after every log would drag a screen reader's cursor there. **`pageHeading` in `dose-writes/focus-after.ts` is the one spelling of "the page's h1 as the last resort"**, and `focusIfLost` focuses it with `{ preventScroll: true }` while every other candidate gets a plain `focus()`: the heading is where focus parks, not a place the user was, so it must not throw a long /log to its top, whereas returning to the control or `focusAfter` should scroll it into view. That is decided by which element it is, not by which candidate named it, so /log's row and the dashboard's Due cards, whose own fallbacks end at the heading, park it the same way. `tests/unit/page-heading-owner.test.ts` scans `src/` for any other h1 lookup, and for the dashboard reaching its h1 by `DASHBOARD_HEADING_ID`.
- **The Undo offer lives in `dose-writes/undo-registry.svelte.ts`, which holds at most ONE, and `Toast.svelte` renders it above the plain toasts.** A successful log offers a delete, posted with `forUndo=1` so a create's Undo keeps no trash row (D8); a successful delete offers a restore carrying the server's `(doseId, deletedAt)` handle. The next successful dose write replaces the offer, which is what removed the "which Undo?" ambiguity and the double click that landed on an older toast's Undo. Otherwise it stays until Undo settles, Dismiss is pressed, a submit for the same dose withdraws it, or its deadline passes — `expiresInMs − 30s` for a restore and `DOSE_UNDO_WINDOW_MS` for a create, both counted from `respondedAt` (the response's arrival, passed to `offerUndo`), never from the end of the reload after it, which has no upper bound and would let the offer outlive the server's window — and never on the 5s timer plain toasts keep, which a keyboard user on /log could not beat and WCAG 2.2.1 counts as a time limit. **A running offer is never replaced or withdrawn, by construction**: Undo takes the layout's lock with `hold()`, so no `acquire()` can succeed until its `extend()`. Toast reads that lock from context once, at init: it is mounted once, in the layout, and lives exactly as long as it, and `getContext` cannot run in a click handler (it throws `lifecycle_outside_component`). An offer never captures a lock, so an Undo pressed after navigating holds the lock the new page's controls read. Undo is refused while another write is `active`; offline it sends nothing and the offer stays and says so; after a network error it stays and becomes usable again once `reloadAfterWrite` finds the server, which is safe because restoring a restored dose succeeds with no change and deleting a deleted one is a 404. When it settles, or is dropped because its deadline passed while the request was in flight, focus moves only if it was lost (the pressed button sits inside the toast stack, which counts as lost), to the offer's `focusTarget` (the restored row's ✎ or Edit), else to what was focused before focus entered the toast stack, else to the page's `h1` (`pageHeading`, focused without scrolling: Chrome focuses a button on a mouse click, so a mouse user's Dismiss or a kept offer expiring ten minutes later would otherwise jump a long /log to its top; `tabindex="-1"` on every signed-in page's h1, because the offer survives navigation and an h1 without it cannot take focus — `tests/unit/page-heading-owner.test.ts` fails on one that lacks it). A press after the deadline — a frozen or backgrounded tab defers the deadline timer — posts nothing, drops the offer the same way and says it is too late: a restore with the server's own 410 words (`RESTORE_GONE_MESSAGE`, in `utils/dose-undo.ts` so both sides read it), a create with `CREATE_UNDO_GONE_MESSAGE`, because "Log it again" would invite a second dose. Dismiss and the deadline timer remove the focused control too, so when focus is inside the stack, and only then, they first hand it to what was focused before the stack, else the `h1`, parked without scrolling; a timer never moves focus that is somewhere else or on `<body>`. No focusout fires for a removed element, so Toast re-reads whether focus is still inside whenever the offer changes, or the plain toasts it was holding would never time out. The button reads "Undo" and is named "Undo" plus the message through `aria-labelledby`, with no sr-only text inside the `role="status"` region, so nothing is announced twice. **The `(app)` layout's `onDestroy` clears the registry and every plain toast** (`resetUndoRegistry`, `clearToasts`): a sign-out leaves `(app)`, and the next person to sign in on a shared device must never see an offer naming the previous person's medication. Clearing is not enough on its own, because sign-in is a client-side navigation and module state survives it: a write whose response lands afterwards would put an offer back. So `resetUndoRegistry` also moves a session generation on, and `watchSession()` — captured when `createDoseWrite`, `runUndo` or `DoseEditForm`'s Save starts, and checked when the response arrives and after every await — makes a write or an Undo that outlives the layout do nothing visible: no offer, no toast, no focus move, no `onSuccess`; it only lets go of the lock (runUndo answers `abandoned`, which Toast shows nothing for). The same predicate is `reloadAfterWrite`'s `cancelled`, so a signed-out tab stops probing `/api/health` and reloads nothing. Every mutator is a no-op when `!browser`, like Toast's list, because module state is per-process during SSR.

- **`src/lib/server/auth/rate-limit-policy.ts` is the one table of protected doors; nothing may hand-write a key.** The implementation was always deep (one atomic upsert), but the interface hid the policy at twenty-five call sites, which is how the browser login door came to throttle by IP alone while `/api/v1/auth/login` throttled by IP **and** email — two doors, one credential, and no test able to compare them. Each policy declares an `identity` (`ip` / `account` / `token`) that carries **no behaviour**: it exists so "what is this budget scoped to?" is answerable by reading the table, because the answer being invisible is what let the doors diverge. The table has **no db import** and the enforcement half re-exports it — twelve suites mock the enforcement module and would otherwise need a database just to name a policy (same split as `appearance/registry.ts` vs `schema.ts`). `tests/unit/rate-limit-registry.test.ts` holds the line: namespaces disjoint, none prefixing another, every policy actually used, and no raw `checkRateLimit` outside the module.
- **`loginAccount` is peeked before the credential check and spent only by failures; every other policy is spent up front.** Counting attempts bounds the attacker _and_ hands anyone who knows an email address a refreshable 15-minute lockout of the real owner — the API door shipped that for months. Counting failures keeps the bound and removes the weapon. A failure is recorded for an **unknown email too**, or the 429 becomes the account-enumeration oracle the dummy Argon2 verify exists to prevent. **`peekLimit` compares `count < max`, not `<=`:** it authorises an attempt that has not happened yet, so reusing `enforceLimit`'s post-increment comparison grants one extra guess (measured: six against a budget of five). `twoFactor` and `preauthBurn` deliberately share one namespace across their two doors — both consume the same signed claim, so a per-door budget would let an attacker spend the allowance twice by switching transport.
- **`src/lib/server/retention.ts` owns every scheduled delete, and they run independently.** They were three consecutive `await`s below two reminder sweeps in the cron handler, so one throw skipped all of them — invisibly, because the loud symptom is the missing reminders. `allSettled` plus a logged failure per policy; it never throws, and the handler re-throws the sweep failure afterwards so a failed tick is still a failed tick. Be exact about the stakes: an expired `rate_limits` row is **already harmless**, because `enforceLimit`'s `CASE` arms restart the window — skipped GC costs table growth, not a locked-out user. What does matter is the `preauth:` carve-out: `rate_limits` doubles as the single-use nonce ledger, so deleting a **live** row would let a captured 2FA challenge token mint a second session. The `dose-log-trash` policy calls `purgeExpiredTrash(db, { now })` from `doses.ts` with no user scope rather than restating its SQL; it runs alongside the on-write purges in `deleteDose` and `restoreDose`, not instead of them, and like them it skips rows another transaction holds.

## Gotchas

- **A form action runs BEFORE the `(app)` group's auth guard, so every action re-checks the user itself.** SvelteKit invokes the action first and the layout `load` only afterwards, which means `+layout.server.ts`'s `if (!locals.user) redirect(...)` has not executed when an action body starts — an anonymous POST reaches `locals.user!.id`, reads `.id` off `null`, and the browser gets a **500 where it should get a 401**. Every action under `src/routes/(app)/` therefore opens with `if (!locals.user) error(401, "Unauthorized")`. `tests/unit/app-action-auth-guard.test.ts` holds the line, and it does two things a per-route test cannot: each case posts a body that would _pass_ its Zod schema (a 400 would short-circuit before `locals.user` and prove nothing), and a coverage test enumerates `Object.keys(actions)` per route so a **newly added action fails the suite until it has a case**. Exactly one exemption, listed there as `EXEMPT`: `settings/security ?/logout`, whose body already sits behind `if (locals.session)` — a 401 there would turn an expired session's clean redirect to `/auth/login` into an error.
- **`src/lib/server/env-contract.js` is the only statement of which env vars must exist, and it is `.js` for a reason.** Two things enforce it: `env.ts` at server boot (against `$env/dynamic/*`) and `scripts/vercel-build.mjs` at build time (against `process.env`), and the build script runs under plain node before any bundler, so a `.ts` contract could not be shared and the list would have to be written twice. It is still typechecked — `allowJs`/`checkJs` are on, so the JSDoc annotations are load-bearing. **Adding a variable to `REQUIRED_PRIVATE_ENV` is a change to the deployment contract, not to a file**: `env.ts` throws at module load, so on Vercel the function dies before routing and _every_ route 500s, `/favicon.ico` included — which is what adding `ENCRYPTION_KEY` did to production on 2026-09-07, while `docs/DEPLOYMENT.md` had listed it as required in production the whole time. Prose is not a check. The build gate covers `production` and `preview` because those are exactly the environments where the server boots with `dev === false`; that mapping is derived from `env.ts`, not chosen, so keep the two in step. `CRON_SECRET` stays out of the list on purpose — see the comment there before adding it. `tests/unit/env-contract.test.ts` holds the single-owner property by asserting neither enforcer contains a literal variable name.
- **Exactly one service worker.** SvelteKit builds `src/service-worker.ts` to `/service-worker.js` and registers it on every page automatically — `kit.serviceWorker.register` defaults to `true`. Never add a second script (e.g. `static/sw.js`) or a manual `navigator.serviceWorker.register(...)`: registrations are keyed by scope, so two scripts at `/` evict each other on every load. Push handlers, `pushsubscriptionchange` and offline caching all belong in that one file.
- Reminder delivery is driven by **two** schedulers hitting `/api/cron/reminders` with the same `CRON_SECRET` bearer: the Vercel cron (daily, Hobby plan cap) and the `reminder-tick` GitHub Actions schedule (every 30 min). `CRON_SECRET` must be set in the Vercel **production** env or the endpoint 500s before doing any work — that outage was silent for four months.
- **The dispatch send path is time-bounded, because the reminder loop is sequential.** `reminders.ts` awaits `withReminderClaim` once per medication in a `for` loop, and the whole tick shares one serverless function budget — so an unbounded send parks every _remaining_ medication, not just its own. `SEND_TIMEOUT_MS` (4s, in `reminders/dispatch.ts`) caps it, and a timeout lands in the same `catch` as a thrown provider error, which is why no extra handling was needed: unresolved intended channels are recorded `failed` and the row stays retryable, while a channel that already succeeded keeps its result and `deriveOverallStatus` resolves the row to `sent` — so a slow push after a delivered email does **not** cause the email to be sent twice. The limit worth knowing: `Promise.race` frees the loop, **not the socket**. A hung request keeps running in the background until the function exits; real cancellation would need an `AbortSignal` threaded into `resend` and `web-push`. The abandoned promise keeps a `.catch()` so a provider that fails long after we gave up cannot surface as an unhandled rejection.
- **A low-inventory alert is scoped to an EPISODE, and exactly one thing re-arms it.** `buildLowInventoryDedupeKey` takes `medications.lowInventoryEpisodeAt`, never the count. With the count in the key the **threshold decided the alert volume** — a descent from a threshold of 10 sent eleven alerts, one per distinct count — and each of those keys then persisted for its row's 90-day life, so a user who refilled and ran low again hit the already-claimed key and was told nothing. The one re-arm is `checkLowInventoryMedications`'s **step-0 UPDATE**, which clears the episode when `inventoryCount` rises **strictly** above `inventoryAlertThreshold` (or either goes NULL). Strictly `>`: `>=` closes the episode of a medication sitting exactly at its threshold and re-alerts forever. It is a predicate on the **count**, deliberately not an anchor into `inventory_events`, because `updateMedicationWithSchedules`, `createMedicationWithSchedules` and `import/apply.ts` all write `inventoryCount` with no ledger row — a user who "refills" by typing into the edit form must still re-arm. It is a **separate global statement** and not part of the loop, because a recovered medication fails the sweep's own `count <= threshold` predicate and so never appears in it. **The episode is opened AFTER the channel gates**, or a user who can receive nothing burns the episode — and under an episode key a burned episode is silent until recovery, not merely until the count next moves, which is why the pre-claim `hasPushSubscriptions` probe is now more load-bearing rather than less. Nudges reuse `computeNagIndex` with `LOW_INVENTORY_NAG_POLICY` (daily, capped at two, so three alerts an episode) and **not** the per-medication `notifyRepeatEveryMinutes`, which paces an overdue _dose_: a medication repeating every 30 minutes would otherwise nag about its stock every 30 minutes. **One clock per tick** — the episode instant is written and later compared by `computeNagIndex`, so sourcing the write from `sql\`now()\``and the comparison from`new Date()` puts two clocks either side of one subtraction. The episode's identity IS its opening instant, which is sufficient only because an episode cannot re-open on the tick that closed it; tests must advance the clock between episodes or a re-opened one collides with its predecessor's key and the assertion passes vacuously.
- `computeOverdueSlot` for `fixed_time` scans back `OVERDUE_LOOKBACK_DAYS` (1) to find the most recent _elapsed_ slot. Evaluating only today's slot silently dropped every schedule timed after the cron tick — permanently, since the local date rolls over before the next tick. A dose at or after the slot satisfies it however late; the tolerance window only extends backwards. **A slot from before local midnight stops reminding once it is `CARRY_OVER_MS` (12h) old.** The constant is imported from `utils/schedule.ts` and is the same bound as the dashboard's `visibleStart`, so the cron falls silent the moment the dashboard hides the row (`reminders-dedupe.test.ts` sweeps both surfaces against each other). It is compared by instant against `startOfDay(now, tz)`, never by day key, so a Godthab slot that rolled past midnight is a today slot on both surfaces. It applies to fixed-time rows only: interval rows remind about the first missed occurrence after the last event, and a cap would silently end them. The cost is accepted: the daily 09:00 UTC Vercel cron now backstops only the 12 hours before it, so if GitHub disables `reminder-tick`, yesterday's daytime slots lose their day-late reminder.
- **`src/lib/utils/push-payload.ts` owns the push wire contract.** Senders build a `PushPayload` (all four fields required) and take their tag from the registry — `overdueTag`, `lowInventoryTag`, `TEST_PUSH_TAG` — never a hand-written string. The service worker reads via `toNotification` and `safeNotificationUrl`, so the fallback logic is unit-testable; the worker itself has no test attach point (jsdom has no `ServiceWorkerGlobalScope`). It lives in `utils/` and not `server/` because the worker imports it.
- Notification `tag`s are a replace-key: showing two notifications with the same tag leaves only the last one. That is why the registry's namespaces must stay disjoint (there is a test), why the test tag must never equal a reminder tag — sharing it would let "send test" silently clear a real reminder out of the tray — and why `toNotification` **omits** the tag for a payload that has none rather than substituting a shared default. A shared default would let two medications' notifications erase one another; untagged ones merely stack.
- **The push wire format is frozen.** Service workers update lazily, so a push can reach a device whose worker predates the deploy. Renaming or restructuring `title`/`body`/`url`/`tag` degrades silently for exactly the users who open the app least. Add fields, never rename them.
- A push the service accepts is not a push the user saw — the OS can suppress it after delivery. The service worker posts `TEST_PUSH_SHOWN_MESSAGE` back to open pages once `showNotification()` resolves for a test, which is the only signal available that it actually rendered. Only test pushes report back; real reminders stay silent.
- Drizzle `numeric` columns return as **string** in JS, not number. `medications.scheduleIntervalHours` and `dosageAmount` must be `Number(...)` before arithmetic.
- **`medications.inventoryCount` is in doses, not raw units — and `dose_logs.inventoryApplied`, not `quantity`, is how much a dose actually took.** `logDose` deducts with `GREATEST(0, count - quantity)` and so cannot take more than there is; `deleteDose` gave back the full `quantity`, so **undoing a dose logged against insufficient stock MINTED the difference**. It needed no unusual input: the dashboard's one-click button sends quantity 1, a medication at 0 is the natural end state of tracking inventory, and undoing that click left a dose in the bottle that was never there — five logs of 10 against an empty bottle restored **50**. `updateDose` was a second door with no delete involved, crediting stock that never left when a clamped dose's quantity was lowered. Editing moves the **applied** amount (`a' = min(newQuantity, previousCount + a)`), never the difference of the two quantities. NULL `inventoryApplied` means the row predates the column, and every reader falls back to `quantity` — that fallback is the correctness guarantee for a `drizzle-kit push`, which applies migration 0020's DDL but skips its backfill `UPDATE`s. **The ledger could not detect any of this**: `inventory_events` reconciles _with_ the mint (`start + Σ quantityChange` equals the wrong count, and the previous→new chain is unbroken), which is why existing drift is not back-correctable and was deliberately left alone. **None of it was testable on `fake-db`**, which stores the Drizzle SQL node verbatim and answers reads from its seed, so it never evaluates `GREATEST` — deleting the clamp outright leaves the whole fake-backed suite green. The arithmetic is decided by the database, so its tests live on PGlite; do not "fix" that by teaching the fake to evaluate SQL, and do not move the arithmetic into TypeScript to buy fake-testability, which would swap one atomic UPDATE for the unlocked read-modify-write CLAUDE.md already warns about for `user_preferences`.
- **`serializeDoseLog` projects field by field and must never go back to `{ ...d }`.** Callers hand it rows from a bare `db.select()` and structural typing lets a wider row through a narrower parameter, so a spread puts every column ever added to `dose_logs` onto the `/api/v1` sync wire and into the JSON export — silently, whatever the signature says. `$lib/types`'s `DoseLog` `Omit`s `inventoryApplied` for the same reason on the client side.
- **Lock order for dose and stock writes: medication rows first (ascending `id` when there are several), then dose or trash rows.** Every per-dose write — `logDose`, `logDoseForSlot`, `logDoseAtSlot`, both skip paths (`logSkippedDose`, `skipDoseForSlot`), `updateDose`, `deleteDose`, `restoreDose` — plus `refillMedication` and `adjustInventory`, locks the medication with `SELECT … FOR UPDATE` before it locks or writes anything else, and `wipeDoseHistory` locks all of the user's medications first with `SELECT id … ORDER BY id FOR UPDATE`. **That is not "every writer of `inventory_count`"**: `import/apply.ts`'s bulk insert and the medication form's absolute `inventoryCount` write (`createMedicationWithSchedules` / `updateMedicationWithSchedules`) stay outside it deliberately — an import is a named blind spot of the since-delete guard, and the form is an overwrite ("set the count to X"), not a delta. The one read allowed ahead of the lock is the unlocked `medication_id` lookup in `deleteDose`, `updateDose` and `restoreDose`, because a dose's medication never changes. Three rules come with it. **Trash purges never wait**: every purge, on write or in retention, is `DELETE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` (`purgeExpiredTrash`), because a user-wide purge otherwise locks other medications' trash rows without their medication locks and closes a cycle with a wipe, a cascade or a restore; Postgres aborts one side with 40P01 and the user gets a 500. Anything a purge skips is purged later. **Clocks that order writes are read AFTER the lock**: `loggedAt` and `deletedAt` come from `new Date()` once the medication row is held, while `takenAt` keeps the action's `now`, because restore's since-delete guard compares the two and only clocks read under the lock follow commit order. **A count that feeds a write is read under the lock**: `refillMedication` and `adjustInventory` used to compute an absolute count from an unlocked read, so a log, delete or restore committing in between was overwritten (a refill reads 6, a restore takes 1, the refill writes 16 and mints one), and unguarded `logDose` could record an `inventoryApplied` larger than what left the bottle, which a later delete then minted. PGlite serialises transactions, so none of this can be raced in a test: cover the losing side by seeding the state it would see, and pin each lock's SQL through `pgDb.queryLog`.
- **A deleted dose moves to `dose_log_trash`, and Undo moves it back; `doses.ts` owns both directions.** `tests/unit/dose-log-trash-owners.test.ts` allows the identifier `doseLogTrash` in exactly `db/schema.ts`, `doses.ts` and `api/wipe.ts`, checked in both directions; `retention.ts` reaches the table only by calling `purgeExpiredTrash`, so the SKIP LOCKED SQL exists once. `deleteDose(userId, doseId, { keepForUndo })` deletes with `RETURNING` and **writes nothing else when no row comes back**: that is what stops two overlapping deletes (Remove racing an Undo, a second tab, the Mac app) crediting stock twice, and `RETURNING`'s committed after-image is why a Save that landed first is credited at its edited amount. The trash row copies every `dose_logs` column except `updatedAt` (`tests/unit/dose-log-trash-columns.test.ts` fails the moment the two drift), plus `inventoryCredited` and `deletedAt`. **`inventoryCredited` is what the delete actually gave back, not a copy of `inventoryApplied`**: the credit is skipped while `inventory_count` is NULL, so it is 0 when tracking was off, and without it a dose deleted with tracking off and restored after tracking came back on would take stock that was never returned. Restore therefore takes back `min(locked count, inventoryCredited)` through `takeFromStock`, the same `GREATEST(0, …)` clamp `insertTakenDose` uses — never `inventoryApplied`, never `quantity`. **The restore contract (D6):** the same id comes back with its original `loggedAt`; it is keyed on `(doseId, deletedAt)`, so an out-of-date Undo cannot reverse a newer delete; it is refused as `logged_since` (409) when any dose of that medication has `loggedAt > deletedAt`, because Remove 08:00, Log now at 08:40, then Undo would otherwise record two taken doses; and it is `gone` (410) once `deleted_at <= now − DOSE_UNDO_WINDOW_MS` — ten minutes, in `utils/dose-undo.ts`, which has no imports so server and client share it. It deletes **every** sync tombstone for the dose: the Mac app applies a delta's upserts before its tombstones, so one surviving tombstone deletes the restored dose there for good. `updateDose` re-reads the dose under the lock and returns null if it has gone, which also closes the ABA a same-id restore opens (Save read applied 3; Remove and Undo re-inserted the dose with a recomputed amount). **Deletes nobody can undo skip the trash (D8)**: `/api/v1 delete_dose`, since the Mac app has no Undo, and the delete behind a create's Undo (`forUndo=1`). Neither the `delete` nor the `restore` audit row carries a diff, so no note text reaches the synced, never-purged audit log. The trash is never exported, which is correct because re-importing a trashed dose would undo its delete, and `ON DELETE CASCADE` from `users` and `medications` clears it through account deletion, the archived-medication wipe and import replace mode, each of which already locks the medication first. The accepted cost is that deleted content stays on the server until the same user's next undoable delete or successful restore, or the `dose-log-trash` retention policy, purges it; see ADR 0008.
- `scheduleType` / `scheduleIntervalHours` columns are marked DEPRECATED in `schema.ts` but still populated and read — the canonical source is the `medication_schedules` table (phase 4d).
- "Days until refill" prefers the schedule rate (`24/intervalHours`) over the 30-day historical average for `scheduleType === "scheduled"`. PRN meds use the historical average.
- **`tests/unit/helpers/fake-db.ts` owns the database seam for unit tests.** Tests mock `$lib/server/db` with `dbMock` and drive it through `fakeDb` — never a hand-rolled chainable. It dispatches on real table identity via drizzle's `getTableName`, so tests import the **real** schema and no test needs to mock `$lib/server/db/schema`. Writes land in two views: `attempted` is append-only (how far execution got before a throw), `committed` is rolled back when a `dbTx.transaction` callback throws (what a database would show afterwards) — `import-apply` asserts on the first, `createMedicationWithSchedules` on the second, and both are correct. `seedReturning` keeps `UPDATE ... RETURNING`'s after-image distinct from what a read sees, which is what `updatePreferences` diffs. `where` predicates are captured, never evaluated; assert on them with `predicateIncludes` (its circular-safe replacer is required — drizzle column nodes point back at their table, so a plain `JSON.stringify` throws). Modules that import `db` but run no query use `unusedDb`, which **throws** on access — do not "upgrade" those to `createFakeDb()`, because that turns a loud accidental query into a silent `[]`. `onConflictDoUpdate`'s config is captured as `RecordedCall.conflict` — for `claimReminderSlot` that upsert IS the dedupe mechanism, so it counts as part of a write's shape. **Exactly one file keeps a bespoke fake, on purpose and commented in place:** `reminders.test.ts` asserts on `whereArgsByCall[1]`, so table dispatch would delete that ordering assertion while leaving the suite green. `auth-totp.test.ts` used to be the second — its update _simulated the production WHERE clause_ — but that simulation is gone: the real compare-and-set now runs against PGlite in `tests/unit/pg/auth-totp.test.ts`, and the original file is on `unusedDb` because everything left in it is pure crypto. Anything else needing predicate evaluation belongs on `pg-db` (below), not in a bigger fake. CI runs with a placeholder `DATABASE_URL`.
- **`tests/unit/helpers/pg-db.ts` is the second backing, and choosing between the two is a rule, not a preference.** Use `fake-db` unless the behaviour under test is _decided by the database_ — either a predicate that gates whether a write happens at all (`checkRateLimit`'s `CASE` arms, `claimReminderSlot`'s `setWhere`, the TOTP compare-and-set), or SQL semantics a fixture cannot model (`jsonb_array_length` on `[]`, `ilike` escaping, `AT TIME ZONE` grouping). Everything else stays on the fake, which is far faster. PGlite files that exercise **production** code live in `tests/unit/pg/`; the helper's own test stays beside the helper as `tests/unit/helpers/pg-db.test.ts`, matching `fake-db.test.ts`. Wherever they live, they have three hard requirements: the `// @vitest-environment node` docblock (the suite default is jsdom, and PGlite takes a browser path when it sees `window`); `vi.useFakeTimers({ toFake: ["Date"] })` if a frozen clock is needed, because faking all timers stalls PGlite's WASM layer; and fixtures seeded via `pgDb.seedUser` → `seedMedication` → `seedDose` / `seedTrash` / `seedTombstone`, in that order, because real Postgres enforces the cascade foreign keys `fake-db` ignored. PGlite runs one backend and serialises transactions, so no test there exercises a race; the lock-order gotcha says how the losing side is covered instead. The helper applies the real `drizzle/` migrations, so those files are now tested too. **PGlite's `now()` follows a faked `Date`** — `vi.useFakeTimers({ toFake: ["Date"] })` moves it, and it is the transaction's start time — so a test proving that an app-stamped column differs from the database default must pass an explicit, different `now`, or both read the same instant and the assertion cannot fail.
- **Svelte 5.57's `render()` from `svelte/server` is LAZY**: a server-render test that never reads `.body` or `.head` renders nothing, so its assertions are vacuous — read the output, and prove the test by breaking the markup it checks.
- `jsonb_array_length(...)` returns 0 for an empty array `[]` — not null. When filtering "with side effects" use `jsonb_array_length(coalesce(side_effects, '[]'::jsonb)) > 0` so both null and empty arrays are excluded.
- **A `LEFT JOIN` whose child predicates sit in the `WHERE` is an inner join wearing a disguise.** The null-extended rows fail the predicate and are discarded, so the parent rows you added the join for disappear again — and it still reads as correct. Child-side conditions belong in the `ON`; that is what `doseLogScope` in `analytics.ts` exists to return unjoined. Two related traps in the same query: `count(*)` counts an unmatched row as 1 (count the child key), and any per-row dispatch must have a branch for the null child.
- SQL `ilike` with user-provided text must escape `%` and `_` (and backslash) before wrapping in `%...%` — see `escapeLikePattern` in `src/routes/(app)/log/+page.server.ts`. Without escaping, a stray `%` in a search term matches everything.
- CSS percentage heights resolve against the parent's _defined_ height. Inside a `flex` container with `items-end`, child columns get content-driven height — so a `height: X%` bar inside collapses to 0. Fix: give the column wrapper `h-full` (or `h-32` etc.) and use `justify-end` on the column itself rather than `items-end` on the parent. See `analytics/+page.svelte` distribution charts for the pattern.
- **`src/lib/utils/schedule-rate.ts` owns the interval rate.** The same quantity lives in two places — `medication_schedules.intervalHours` and the parallel legacy column `medications.scheduleIntervalHours` — and every reader of either takes `parseIntervalHours` / `intervalDosesPerDay` from this module rather than spelling its own guard: `intervalHours` is a Drizzle `numeric` and arrives as a **string**, so `if (!intervalHours)` does not reject `"0"`. Six sites on the schedule-rows path wrote that guard differently and `computeOverdueSlot` got it wrong, reporting a medication overdue the instant it was logged; four more on the legacy-column path repeated it. `src/lib/utils/adherence.ts` shares the `parseIntervalHours` guard but deliberately keeps its own 1-per-day fallback instead of the primitive's 0 — don't "fix" that into `intervalDosesPerDay`. It lives in `utils/` and not `server/` because `utils/time.ts` and `utils/schedule.ts` are client-reachable.
- **`MAX_INTERVAL_HOURS` is a door policy, not a read policy.** Apply it in the two Zod schemas and the import gate only. A stored 168 (weekly injection) predates the bound and must still produce a rate — rejecting it on read would drop that medication out of refill forecasting, out of the adherence denominator and out of reminders. Apply it to the _parsed number_, never the raw string.
- **`medicationStatsFor`'s `legacyRate` is not a duplicate of `dailyRateFor`.** `expectedDailyDoses` is the adherence denominator and must be `null` when a medication has no scheduled rate; `dailyRateFor` always returns a number, falling back to `thirtyDayDoseCount / 30`. Substituting it would draw an adherence bar measuring a PRN user against their own past behaviour.

## Styling

Tailwind CSS v4 with custom theme in `src/app.css`. Dark-mode-first. Key tokens: `glass`, `surface`, `surface-raised`, `text-primary`, `text-secondary`, `accent`.

- **A colour splits three ways by ROLE, and the roles are not interchangeable.** `accent` = fill (`bg-`), `accent-ink` = text/border/ring, `accent-fg` = the foreground that sits _on_ the fill. `danger` splits identically (`danger` / `danger-ink` / `danger-fg`). No single value does two jobs: `#4f46e5` is 1.99:1 as text and `#8f92f5` is 2.76:1 with white on it. `success` and `warning` need no ink variant — they already clear both.
- **`--color-info` is deliberately a separate token from `--color-accent-ink` even when they hold the same value.** The ink moves with the user's accent; info must not, or an amber accent turns every neutral "info" chip amber and it collides with `warning`. Do not simplify them into one.
- **`--color-glass-border` is decorative; `--color-border-strong` is the control boundary.** The hairline is 1.33:1 and cannot satisfy WCAG 1.4.11's 3:1, so any interactive control's resting border takes `border-strong`.
- **`src/routes/(app)/+layout.svelte` sets `--color-accent`, `--color-accent-fg` and `--color-accent-ink` as inline styles from `data.preferences.accentColor`, and inline beats every stylesheet rule.** So a value changed in `@theme` does NOT change inside the authenticated app — `@theme`'s accent values are the logged-out fallback, and the value that reaches real users is the column default in `schema.ts`. `accent-fg`/`accent-ink` are derived by `readableForeground`/`readableInk` in `src/lib/utils/contrast.ts`, the single WCAG implementation; never hand-roll the maths.
- `tests/unit/theme-tokens.test.ts` parses `src/app.css` (both `@theme` and the `prefers-contrast` block) and reads the accent presets from `entryFor("accentColor").presets` in the appearance registry, so it cannot drift from what ships. It asserts text tokens, fills, control boundaries and the tinted `/10 /15 /20` chips against the backdrop each actually composites onto — a new chip combination belongs in that table, with its real DOM nesting.
- **The theme is an SSR `<style id="theme-tokens">` block emitted from `(app)/+layout.svelte`, at `:root:root` specificity.** Three parts are load-bearing and none is stylistic. **`:root:root` (0,2,0)** is insurance, not the active defence: this block is unlayered and app.css's `prefers-contrast` overrides now live inside `@layer theme`, so an unlayered normal declaration already beats them regardless of specificity — the layer alone decides it today. The extra specificity only matters if that block is ever unlayered again, in which case `:root:root` still beats a plain `:root` regardless of head order, where equal specificity would not: measured while both were unlayered, the winner flipped between an SSR load (Kit emits head content before stylesheet links) and a client-side nav (Svelte appends after), so a plain F5 changed the palette, and on the SSR path the losing side was the accessible one. **The block is built in `src/lib/appearance/theme-css.ts`, not inline**, because the literal characters `</style>` in a `.svelte` file break `npm run check`; the closing tag is split. **`{@html}` applies zero escaping and CSP does not cover CSS injection** — a pure-CSS payload needs no tag break to exfiltrate via `background-image: url(...)` under our `img-src`, so the accent is re-tested against `/^#[0-9a-f]{6}$/i` at the interpolation site, stricter than `contrast.ts`'s `HEX_RE` (which takes 3-digit hex) and stricter than the column (a bare `text()`).
- **The palette exists twice and neither copy generates the other**: `@layer theme` in `app.css` serves `system` and every logged-out route; `LIGHT_TOKENS`/`DARK_TOKENS` in `theme-css.ts` serve the explicit choices. `tests/unit/theme-css.test.ts` asserts they are identical. **`@layer theme` is Tailwind's LOWEST layer** (`@layer theme, base, components, utilities;`), which is what lets the unlayered SSR block win — and is why `color-scheme` had to move out of `@layer base`, since `base` outranks `theme` and a layered light arm could never have overridden it.
- **`data-density` and `data-reduced-motion` stay on the `(app)` wrapper div.** They cannot move to the theme block: `Heatmap.svelte`'s override targets a Svelte-scoped `.heatmap-cell.svelte-<hash>`, and the hash is content-derived. The theme block emits only colour tokens and `color-scheme`; these set only spacing and animation timing. Disjoint by construction — keep it that way.
