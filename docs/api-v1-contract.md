# `/api/v1` contract

Source of truth for the native macOS client (`medtracker-mac`, separate repo). This
document is generated by reading the actual implementation — not aspirational. If this
file and the code ever disagree, the code wins; update this file to match.

Implementation lives at:

- Routes: `src/routes/api/v1/**/+server.ts`
- Domain glue: `src/lib/server/api/{auth,sync,commands,export,serialize,preauth,apple,wipe}.ts`
- Payload schemas: `src/lib/utils/validation.ts`
- Tables added for this surface: `src/lib/server/db/schema.ts` (`syncTombstones`, `apiCommands`,
  `users.syncEpoch`, `doseLogs.updatedAt`)

## 1. Base path and auth

- Base path: `/api/v1`
- Every route except `POST /auth/login`, `POST /auth/2fa`, and `POST /auth/apple` requires:

  ```
  Authorization: Bearer <token>
  ```

  `<token>` is a **Lucia session id** — the same `token` string returned by
  `login`/`2fa`/`apple`, not a JWT. It is validated with `lucia.validateSession(sessionId)`
  (`src/lib/server/api/auth.ts:resolveApiUser`), i.e. the exact same session store the web
  app's cookie-based sessions use. There is no separate API-token table.

- `requireApiUser(request)` throws `401` (see §6 for the error body shape) when the header
  is missing, doesn't start with `Bearer `, or the session id doesn't resolve to a live
  session/user.

## 2. Auth endpoints

### `POST /auth/login`

Body (`loginSchema`):

```ts
{
  email: string;
  password: string;
} // email: must be a valid email; password: non-empty
```

- Rate-limited per lower-cased email: **5 attempts / 15 minutes** (`checkRateLimit("api-login:<email>", 5, 15*60*1000)`). Exceeding it returns `429` (see §6).
- `400` if the body fails `loginSchema` validation — body `{ message: "Invalid credentials payload" }`.
- `401` if the email doesn't exist or the password is wrong (uniform message, no email
  enumeration) — body `{ message: "Invalid email or password" }`.
- If `user.twoFactorEnabled`, returns **200** with a TOTP challenge instead of a session:

  ```ts
  {
    challenge: "totp";
    preAuthToken: string;
  }
  ```

  `preAuthToken` is an HMAC-signed, **5-minute-TTL** token (`signPreAuthToken`,
  `src/lib/server/api/preauth.ts`) — not a session token. Pass it to `/auth/2fa`.

- Otherwise returns **200**:

  ```ts
  {
    token: string;
    user: SessionUser;
  }
  ```

  `token` is a new Lucia session id (`lucia.createSession(user.id, {})`).

### `POST /auth/2fa`

Body:

```ts
{
  preAuthToken: string;
  code: string;
} // code: must match /^\d{6}$/
```

- `400` if the body fails validation (e.g. code isn't 6 digits) — `{ message: "Invalid payload" }`.
- `401` if the pre-auth token is invalid/expired/tampered — `{ message: "Challenge expired — sign in again" }`.
- `401` if the TOTP code is wrong (via `verifyAndConsumeTOTPCode`, which also enforces the
  RFC 6238 replay guard against `totpLastCounter`) — `{ message: "Invalid code" }`.
- `401` if the user backing the pre-auth token no longer exists — `{ message: "Unknown user" }`.
- Otherwise **200**: `{ token: string; user: SessionUser }` (new Lucia session, same shape as login).

### `POST /auth/apple`

Body:

```ts
{ identityToken: string; fullName?: string } // fullName: max 200 chars
```

`identityToken` is the native Sign in with Apple identity token (verified server-side
against Apple's JWKS via `verifyAppleIdentityToken`, checking issuer `https://appleid.apple.com`
and audience `APPLE_CLIENT_ID`). This is the **native token flow only** — there is no web
redirect flow implemented in `/api/v1` (deferred).

- `400` if the body fails validation — `{ message: "Invalid payload" }`.
- `401` if the identity token fails verification — `{ message: "Invalid Apple token" }`.
- Three outcomes after verification, checked in order:
  1. **Existing Apple link** (`oauth_accounts` row for `provider="apple"` +
     `providerUserId=<apple sub>`) → signs in that user. **200**: `{ token, user }`.
  2. **No link, but the Apple account's email matches an existing (non-Apple) user** → refuses
     to auto-link. **409**, body `{ message: "email_conflict" }` (see §6 — this is a
     `throw error(409, "email_conflict")`, so it uses the `{ message }` shape, with the message
     text itself being the literal string `"email_conflict"`).
  3. **No link, no email collision** → creates a brand-new user (`passwordHash: null`,
     `emailVerified` taken from Apple's claim) + a new `oauth_accounts` link, then signs in.
     If Apple didn't share an email (relay-hidden), a synthetic
     `<appleUserId>@privaterelay.appleid.com` address is used. **200**: `{ token, user }`.

### The `user` object (`SessionUser`, via `toSessionUser`)

Returned by all three auth endpoints (`src/lib/server/api/serialize.ts:toSessionUser`):

```ts
{
  id: string;
  email: string;
  name: string;
  avatarUrl: string | null;
  timezone: string;
  twoFactorEnabled: boolean;
  emailVerified: boolean;
}
```

## 3. `GET /sync`

Delta pull for the native client. Auth required.

**Query params:**

| param   | type                          | meaning                                                                                                   |
| ------- | ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| `since` | ISO datetime, optional        | cursor from a previous sync response's `cursor` field. Omit for the first sync.                           |
| `epoch` | integer, optional (default 0) | the client's last-seen `epoch` value. Compared against the server's current epoch to decide `fullResync`. |

**Response (`SyncResponse`, `src/lib/server/api/sync.ts`):**

```ts
{
  epoch: number;               // current server-side users.syncEpoch
  fullResync: boolean;         // see below
  serverTime: string;          // ISO, this request's timestamp
  cursor: string;              // == serverTime — pass back as `since` next call
  medications: Array<SerializedMedication & { schedules: SerializedSchedule[] }>;
  doseLogs: SerializedDoseLog[];
  inventoryEvents: SerializedInventoryEvent[];
  auditLogs: SerializedAuditLog[];
  tombstones: SerializedTombstone[];
  preferences: SerializedPreferences | null;
  profile: SessionUser | null;
}
```

### Cursor semantics

- **`cursor`** is simply the server's timestamp at response time (`serverTime`). Pass it back
  as `since` on the next call. There is no separate cursor table/token — it's a plain
  "give me everything with a change-timestamp greater than this instant" watermark.
- Per-table cursor column:
  - `medications`, `dose_logs`: filtered by `updated_at > since` (both are edited in place).
  - `inventory_events`, `audit_logs`: filtered by `created_at > since` (append-only).
  - `sync_tombstones`: filtered by `deleted_at > since`.
  - `medication_schedules`: **no independent cursor.** Each returned medication carries its
    **full current set** of schedule rows as a `schedules` child array (via
    `getSchedulesForUser`, scoped only by `userId` — not by `since` and not filtered by the
    medication's archived state). This sidesteps `medication_schedules` not having its own
    `updated_at` column. Consequence: a medication only appears in a delta sync (and thus its
    schedules only refresh) when the _medication_ row itself changed since `since`; a schedule
    edited without touching the parent medication's `updated_at` will not be picked up by a
    delta call under this row-level design — rely on `fullResync` / full sync for that case
    if it's ever observed.
  - `users`, `user_preferences`: **always returned in full**, ignoring `since` entirely —
    `profile` and `preferences` are singleton rows per user, so there's nothing to page.

### `fullResync`

`fullResync = !since || clientEpoch < server epoch`. When `true`, the server ignores the
`since` query param entirely and returns **every** row for every table (tombstones are the
one exception — see below). The client must **discard all local data** for this account and
replace it wholesale with the response. This happens when:

- it's the client's first sync (no `since`), or
- the server's `syncEpoch` has advanced past what the client last recorded — see §4, wipes
  bump this epoch.

### Tombstones

`tombstones` are **only ever populated when `since` was set** (i.e. never on a full resync —
on a full resync the client is rebuilding from nothing, so there's nothing to delete).
Shape (`SerializedTombstone`):

```ts
{
  id: string;
  userId: string;
  entityType: string;
  entityId: string;
  deletedAt: string; /* ISO */
}
```

`entityType` is one of `"medication" | "dose_log" | "medication_schedule" | "inventory_event"`
(per the comment on `syncTombstones` in `schema.ts`; not DB-enforced).

### Numeric-as-string fields

Drizzle's `numeric` Postgres columns come back as **strings**, and the serializers pass them
through unchanged (the Swift client is expected to parse to `Decimal` itself). Affected fields:

- `medications.dosageAmount` — string, e.g. `"50"` or `"12.5"`
- `medications.scheduleIntervalHours` — string or `null` (DEPRECATED column, still populated)
- `medication_schedules[].intervalHours` — string or `null`

All `Date` columns are serialized to ISO 8601 strings (`Date.toISOString()`); `null` dates
stay `null`.

### Serialized shapes (field-for-field)

**`SerializedMedication`** (`serializeMedication`) — spreads the raw `medications` row, then
overrides date fields to ISO strings:

```ts
{
  id: string; userId: string; name: string;
  dosageAmount: string; dosageUnit: string; form: string; category: string;
  colour: string; colourSecondary: string | null; pattern: string; notes: string | null;
  scheduleType: string;               // DEPRECATED, still populated: "scheduled" | "as_needed"
  scheduleIntervalHours: string | null; // DEPRECATED, still populated
  inventoryCount: number | null; inventoryAlertThreshold: number | null;
  sortOrder: number; isArchived: boolean;
  archivedAt: string | null; startedAt: string; endedAt: string | null;
  createdAt: string; updatedAt: string;
  schedules: SerializedSchedule[];    // attached by buildSyncResponse, not part of the row itself
}
```

**`SerializedSchedule`** (`serializeSchedule`):

```ts
{
  id: string; medicationId: string; userId: string;
  scheduleKind: "fixed_time" | "interval" | "prn";
  timeOfDay: string | null;      // "HH:mm", fixed_time only
  intervalHours: string | null;  // numeric-as-string, interval only
  daysOfWeek: number[] | null;   // 0-6, fixed_time only, null = every day
  sortOrder: number;
  effectiveFrom: string; effectiveTo: string | null; createdAt: string;

```

**`SerializedDoseLog`** (`serializeDoseLog`):

  quantityChange: number; // signed delta

  newCount: number | null;

**`SerializedAuditLog`** (`serializeAuditLog`):

```ts
{
  id: string;
  userId: string;
  entityType: string;
  entityId: string;
  action: string;

```

**`SerializedPreferences`** (`serializePreferences`):

```ts
{
  userId: string;
  accentColor: string;
  dateFormat: "DD/MM/YYYY" | "MM/DD/YYYY" | "YYYY-MM-DD";
  timeFormat: "12h" | "24h";
  uiDensity: "comfortable" | "compact";
  reducedMotion: boolean;
  overdueEmailReminders: boolean;
  overduePushReminders: boolean;
  lowInventoryEmailAlerts: boolean;

  heatmapPeriod: number;
  exportFormat: "pdf" | "csv";
  updatedAt: string;
}
```

## 4. `POST /commands`

Batched, idempotent write endpoint. Auth required.

**Body:**

```ts
{
  commands: Array<{ id: string; type: string; payload: unknown }>;
} // max 200 commands per request
```

`id` is empty-string-rejected (`min(1)`); it is the **client-generated idempotency key**,
unique per `(userId, id)`. `400` if the body fails this envelope schema — `{ message: "Invalid commands payload" }`.
Per-command `payload` validation happens inside each handler (a Zod `.parse()` failure there
is caught and surfaces as that command's `ok:false` result — see below — not a 400 for the
whole request).

**Response:**

```ts
{
  results: Array<{ id: string; ok: boolean; result?: unknown; error?: string }>;
}
```

Always **200**, even when individual commands fail — failures are per-command, not
transport-level.

### Idempotency / replay semantics (`runCommands`, reserve-first algorithm)

For each command, `(userId, id)` is the primary key into the `api_commands` ledger table:

1. **Reserve**: `INSERT ... ON CONFLICT DO NOTHING` with `result: null`. Only one caller ever
   wins this insert for a given `(userId, id)`.
2. **Winner dispatches** the command's handler.
   - **Success** → the mutation is durably committed. The ledger row is updated with the
     result (best-effort — if that update itself fails, the row is deliberately left with
     `result: null` rather than deleted, since the mutation already happened and must not be
     retried). Response: `{ id, ok: true, result }`.
   - **Throw** (validation error, domain error, `UnknownCommandError`) → the reservation row
     is deleted (safe, because every handler's domain function is all-or-nothing — nothing
     durable happened). Response: `{ id, ok: false, error: <e.message> }`. **This is
     retryable** — resubmit the same `id` to retry.
3. **Loser** (the insert hit the conflict, i.e. this `id` was already seen):
   - If the existing row has a non-null `result` → the command already completed. Response:
     `{ id, ok: true, result: <cached result> }` (replay, handler is **not** re-invoked).
   - If the existing row's `result` is still `null` → another attempt is mid-flight (or died
     without cleaning up). Response: `{ id, ok: false, error: "in_progress" }`. The client
     should **not** blindly retry this id in a tight loop; back off and/or reconcile actual
     state via `/sync`.

- `{ scheduleKind: "prn" }`

### Wipes bump the sync epoch

`wipe_dose_history` and `wipe_archived_medications` (`src/lib/server/api/wipe.ts`) each run
their delete + `users.syncEpoch + 1` + an audit-log row (`entityId: "*"`) inside **one
transaction**, so they can never partially apply. Native clients cannot delta-sync a bulk
delete (there's no per-row tombstone for a wipe), so **the client must call `/sync` with no
`since` (or notice `fullResync: true` on its next `/sync` call, since its remembered epoch is
now behind) after either wipe** to pick up the deletion.

## 5. `GET /export/full`

Full-account JSON backup / data-portability endpoint. Auth required. Reuses
`buildSyncResponse(userId, null, 0)` internally (the full-resync path), so the export is
always exactly what a client would get from a from-scratch `/sync` call, plus a version
envelope. This is distinct from the web app's `/api/export` CSV/PDF dose export.

- Rate-limited per user id: **10 requests / 15 minutes** (`checkRateLimit("api-export:<userId>", 10, 15*60*1000)`). `429` on limit (see §6).
- **200** response headers:
  - `content-type: application/json`
  - `content-disposition: attachment; filename="medtracker-backup-<YYYY-MM-DD>.json"` (date = today, UTC)
- Body (`FullExport`, `src/lib/server/api/export.ts`):

  ```ts
  {
    version: 1;
    exportedAt: string;       // ISO, == the underlying sync response's serverTime
    profile: SessionUser | null;
    preferences: SerializedPreferences | null;
    medications: Array<SerializedMedication & { schedules: SerializedSchedule[] }>;
    doseLogs: SerializedDoseLog[];
    inventoryEvents: SerializedInventoryEvent[];
    auditLogs: SerializedAuditLog[];
  }
  ```

  Note: no `tombstones`, `epoch`, `fullResync`, or `cursor` fields — those are sync-protocol
  plumbing, not meaningful in a standalone backup file.

## 6. Error shapes

**Two distinct shapes exist across this surface — the client must branch on which one it got.**

### A. Thrown SvelteKit errors (`throw error(status, "message")`)

Used for `400`, `401`, `409`. Body:

```ts
{
  message: string;
}
```

Examples actually produced by this code:

| status  | body                                               | where                                                                                        |
| ------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 400     | `{ message: "Invalid credentials payload" }`       | `POST /auth/login`, bad body                                                                 |
| 400     | `{ message: "Invalid payload" }`                   | `POST /auth/2fa`, bad body                                                                   |
| 400     | `{ message: "Invalid payload" }`                   | `POST /auth/apple`, bad body                                                                 |
| 400     | `{ message: "Invalid commands payload" }`          | `POST /commands`, bad envelope                                                               |
| 401     | `{ message: "Invalid email or password" }`         | `POST /auth/login`                                                                           |
| 401     | `{ message: "Challenge expired — sign in again" }` | `POST /auth/2fa`, bad/expired preAuthToken                                                   |
| 401     | `{ message: "Invalid code" }`                      | `POST /auth/2fa`, wrong TOTP code                                                            |
| 401     | `{ message: "Unknown user" }`                      | `POST /auth/2fa`, user deleted between login and 2fa                                         |
| 401     | `{ message: "Invalid Apple token" }`               | `POST /auth/apple`                                                                           |
| 401     | `{ message: "Unauthorized" }`                      | any authed route, missing/invalid bearer token (`requireApiUser`)                            |
| **409** | `{ message: "email_conflict" }`                    | `POST /auth/apple`, Apple account's email already belongs to a different (non-Apple) account |

### B. Rate-limit responses (constructed directly, not via `error()`)

Used for `429` on `/auth/login` and `/export/full`. Body:

```ts
{
  error: "rate_limited";
  retryAfterSeconds: number;
}
```

Plus a `Retry-After` response header (same integer, as a string). **Note the different key
name** (`error`, not `message`) from shape A — this is deliberate in the source (see
`src/routes/api/v1/auth/login/+server.ts` and `.../export/full/+server.ts`), not an inconsistency
to normalize away; the client must check for `error === "rate_limited"` on 429s and
`message` on the thrown-error statuses.

## 7. Migrations added for this surface

All in `drizzle/0014_moaning_gladiator.sql`:

- `ALTER TABLE dose_logs ADD COLUMN updated_at timestamptz DEFAULT now() NOT NULL` (+
  backfilled from `logged_at` where later, + index `dose_logs_user_updated_idx`) — dedicated
  delta-sync cursor for dose logs, distinct from the user-facing `taken_at`/`logged_at`.
- `ALTER TABLE users ADD COLUMN sync_epoch integer DEFAULT 0 NOT NULL` — bumped on destructive
  server-side operations (currently: the two wipe commands) that fall outside normal per-row
  `updated_at` tracking; drives `fullResync` in `/sync`.
- `CREATE TABLE sync_tombstones (id, user_id, entity_type, entity_id, deleted_at)` + index
  `sync_tombstones_user_deleted_idx (user_id, deleted_at)` — deletion records for synced
  entities so clients can prune what the server no longer has.
- `CREATE TABLE api_commands (user_id, idempotency_key, result jsonb, created_at, PRIMARY KEY
(user_id, idempotency_key))` — the idempotency ledger backing `POST /commands` (§4).
